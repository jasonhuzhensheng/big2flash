2.0 做了什么

  • MTP 推测解码。Qwen3.8 自带一个多 token 预测层，先猜下一个 token，主模型一次前向同时验证两个位置。读权重的开销几乎不变，接受时一步出两个 token。
  • 输出不变。贪心模式下与普通解码逐 token 一致（已在 k=1–4 和服务器开/关 MTP 下核对）；采样模式用标准的接受/重采样规则，分布与普通采样相同。
  • 线性注意力层可回滚。验证时逐 token 保存递归状态，猜错时恢复到最后接受的位置；全注意力层直接截断 KV 缓存。多轮对话的缓存复用照常工作。
  • 权重锁进内存。没锁时 mmap 权重只能读到约 40 GB/s，锁住后接近 355 GB/s。
  • 增量解码文本。8K 上下文时每 token 从 1.3 ms 降到 0.004 ms；停止词只查尾部。
  • 按显存自动限制上下文和预填充分块，长上下文不再爆内存。
  • 体积。App 1 MB；运行环境去掉 torch，只剩 365 MB。

读数时要注意

  • 模型文件不完全相同：MLX 4-bit 15.1 GB，GGUF 约 17 GB；LM Studio 用的是 huihui 去审查微调版。同规格 Q4，但不是同一份权重。
  • MTP 的收益取决于内容：代码、结构化文本接受率高（原型里 22→30 tok/s），开放式写作低一些。
  • k=1（每步猜 1 个）最快；猜 2–3 个时验证开销超过收益。
  • 短提示的“预填充速度”只有 20–60 个 token，没有意义，表里没列。
  • 这台机器上后台服务会间歇占用 GPU，同一配置重复跑有约 ±10% 波动。上午第一轮 big2flash MTP 测到 27.37 / 28.15，这次是 24.04 / 25.33；Ollama 长提示从 21.21 变成 24.76。长提示上 big2flash 和 Ollama 的差距在波动范围内。
  • 预填充 big2flash 和 mlx-lm 用同一套 MLX 算子，差距是噪声；两者都比 llama.cpp 系快 20–30%。
  • 采样模式（温度 > 0）经服务器实测 15–19 tok/s，低于贪心。

测试脚本在 tests/bench/：run_all.sh 依次单独启动每个引擎，engines.py 用流式 HTTP 从客户端计时（首字时间含预填充；生成速度 = (token 数 − 1) ÷ 首末 token 间隔），结果写入 engines.jsonl。
